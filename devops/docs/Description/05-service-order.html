05 — Order Service

Order orchestration using a Kafka Saga (choreography) across services.

Port: 8083 · Stack: Spring Boot, MySQL, Kafka

What it does

  • POST /api/orders — create an order (JWT); inventory is reserved asynchronously
  • GET /api/orders/status/{orderNo} — poll until CONFIRMED or FAILED
  • POST /api/orders/{orderNo}/cancel — cancel
  • POST /api/orders/demo/concurrent-create — concurrency demo

The Saga

POST /orders ─► publish order-created ─────────────► Inventory reserves
                                                          │
        order-confirmed ◄── consume inventory-reserved ◄──┤
        order-failed    ◄── consume inventory-failed   ◄──┘
Topic Role
order-created published on new order
inventory-reserved / inventory-failed consumed from Inventory
order-confirmed / order-failed published when the saga settles
order-dlq dead letter after consumer retries are exhausted

Design decisions

  • Choreography, not orchestration. Services react to events instead of a central coordinator — loose coupling, each service owns its state.
  • Dead-letter queue + retries. Failed messages are retried with backoff, then routed to a DLQ rather than blocking the partition.
  • Eventual consistency. The order moves PENDING → CONFIRMED/FAILED as events arrive; the API exposes status polling.

Why it matters (skills shown)

Distributed transactions without 2PC, event-driven design, failure isolation (DLQ), and reasoning about eventual consistency.
