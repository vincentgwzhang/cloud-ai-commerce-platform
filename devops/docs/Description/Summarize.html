Building a Cloud-Native AI Commerce Platform (Solo Project)

Over the past weeks I built a production-style microservices platform end to end — from event-driven backend services to GitOps delivery, full observability, and an AI assistant that answers questions grounded in real product data. Here’s what it does and what I learned.

Stack: Java 25, Spring Boot 4, Spring Cloud, MySQL, Redis, Apache Kafka, Kubernetes (Minikube), Helm, Argo CD, Bitnami Sealed Secrets, Prometheus, Grafana, OpenTelemetry, OpenAI + ChromaDB.

The architecture

Six independently deployable services sit behind an API gateway and communicate over REST and Kafka:

  • Auth (8080) — stateless RS256 JWT: login, refresh-token rotation, validate.
  • Product (8081) — catalog with Redis cache-aside, stampede protection, TTL jitter.
  • Inventory (8082) — reservations with anti-overselling, idempotency, optimistic locking.
  • Order (8083) — order orchestration as a Kafka Saga (choreography) with dead-letter handling.
  • AI (8084) — chat with memory + Retrieval-Augmented Generation over the catalog.
  • Gateway (8088) — single entry point via Spring Cloud Gateway.

Three ways to deploy — all idempotent

The same platform ships three ways, which forced me to really understand each layer:

  • Raw kubectl — Deployments, Services, ConfigMaps and Secrets applied directly; images built straight into Minikube’s Docker daemon.
  • Helm — all six services collapsed into one parameterized chart (one values file, templated manifests, upgrade --install).
  • Argo CD (GitOps) — Git is the single source of truth; Argo CD continuously reconciles the cluster to the chart in the repo.

Secrets in Git, safely

GitOps wants everything in Git, but you must never commit a plaintext API key. I used Bitnami Sealed Secrets: the OpenAI key is encrypted client-side into ciphertext that is safe to commit (even publicly) and only the in-cluster controller can decrypt it. Push the ciphertext → Argo CD syncs it → the controller materializes the real Kubernetes Secret.

The AI part: RAG with clean boundaries

The AI service answers natural-language questions about products. The key design choice was keeping service boundaries clean: product data stays owned by the Product service, while the AI service maintains an eventually-consistent vector replica synchronized through Kafka product events — no cross-service database reads.

A question is embedded, matched against ChromaDB via similarity search, and the top results are turned into a grounded prompt for the LLM. The answer cites the source product codes, so it’s traceable rather than hallucinated. Embedding, vector store, and LLM all sit behind interfaces, so each can be swapped without touching the pipeline.

Observability by default

Every service exposes Prometheus metrics and trace-correlated logs. Micrometer feeds Prometheus, Grafana renders a provisioned dashboard (availability, HTTP latency, cache hit/miss, Kafka consume/publish), and an OpenTelemetry trace ID flows into the logs so a single request can be followed across services.

What I learned

  • Designing token lifecycles and a public/private-key trust boundary that five services reuse.
  • Distributed transactions without two-phase commit — Kafka Saga, idempotency, and dead-letter queues.
  • The real differences between kubectl, Helm and GitOps — and the operational gotchas (CRDs too large for client-side apply, branch mismatches, Argo CD fighting manual changes).
  • Shipping secrets through GitOps without leaking them.
  • Integrating an LLM pragmatically: embeddings, vector search, prompt grounding, and resilience around a third-party API.
