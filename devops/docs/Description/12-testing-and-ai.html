12 — Testing & Using the AI

How the platform is tested, and how to actually drive the AI features end to end.

Testing strategy

Layer Tooling Example
Unit JUnit, Mockito JwtServiceTest, RefreshTokenServiceTest
Integration Spring Boot Test, Testcontainers AuthApiIntegrationTest, Product cache tests against real Redis
Coverage gate JaCoCo build fails under 80% (Auth 85%) 
mvn test verify          # whole platform
mvn -pl AuthService test verify
xdg-open AuthService/target/site/jacoco/index.html   # coverage report

Why Testcontainers: cache and auth behavior are verified against real Redis/DB instances spun up per test run, not mocks — far closer to production behavior.

Manual API testing

A Postman collection (postman/) covers Auth → Product → Inventory with an environment that auto-saves tokens. The typical flow:

# 1) get a token
TOKEN=$(curl -s -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"vincent","password":"123456"}' | jq -r .accessToken)

# 2) call a protected API
curl -s http://localhost:8081/api/v1/products -H "Authorization: Bearer $TOKEN" | jq

Using the AI service

Prerequisites for full AI: Kafka + ChromaDB running, and OPENAI_API_KEY provided.

docker compose -f devops/script/docker-compose-app.yml up -d                    # Kafka
docker compose -f devops/script/docker-compose-observability-local.yml up -d    # includes Chroma

1. Chat (with memory)

curl -s -X POST http://localhost:8084/api/v1/ai/chat \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"message":"Hi, recommend a phone","conversationId":null}' | jq

The response returns a conversationId; pass it back on the next turn to keep context. History is stored in Redis with a sliding TTL.

2. Product RAG

First, product events flow Product → Kafka → AI, which embeds them into ChromaDB. Then ask in natural language:

curl -s -X POST http://localhost:8084/api/v1/ai/ask \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"question":"Which products are good for gaming under a tight budget?"}' | jq

The answer is grounded in real catalog data — the service embeds the question, runs a similarity search in ChromaDB, builds a prompt from the top matches, and asks OpenAI. The response includes the source product codes so answers are traceable, not hallucinated.

How I validated the vector store

The ChromaDB integration (v2 API) was verified directly against a running Chroma container with a full create-collection → upsert → similarity-query → delete round trip before wiring it into the service — proving the riskiest piece independently of the rest of the stack.

Why it matters (skills shown)

A test pyramid with real-dependency integration tests and coverage gates, plus hands-on LLM application testing (embeddings, vector similarity, prompt grounding, source attribution).
