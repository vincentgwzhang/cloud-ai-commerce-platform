02 — Auth Service

Stateless authentication and the trust anchor for the whole platform.

Port: 8080 · Stack: Spring Boot, Spring Security, MySQL · Tokens: RS256 JWT + opaque refresh tokens

What it does

  • POST /api/v1/auth/login — verify credentials (BCrypt), issue an access JWT + a refresh token
  • POST /api/v1/auth/refresh — rotate tokens (the presented refresh token is revoked, a new pair issued)
  • GET /api/v1/auth/validate — validate a Bearer JWT, return username + role
  • GET /api/v1/auth/health — liveness

Design decisions

  • Asymmetric JWT (RS256). Auth holds the private key and signs; every other service verifies with the public key only. No shared secret, and downstream services validate tokens offline — no network call back to Auth on every request.
  • Refresh-token rotation with reuse detection. Refresh tokens are opaque and stored in MySQL (refresh_tokens). Each refresh revokes the old token and issues a new one; replaying an old token returns 401. A fresh login revokes the user's active tokens (single-session policy).
  • Stateless access path. Access JWTs are short-lived (1h); refresh tokens last 7 days.
login ─► access JWT (1h, RS256)  +  refresh token (7d, opaque, in MySQL)
access expires ─► /refresh (rotates) ─► new access + new refresh

Why it matters (skills shown)

Token lifecycle design, public/private key cryptography, Spring Security configuration, and a clean security boundary that the other five services reuse.

Quality

Unit + integration tests (AuthApiIntegrationTest covers login, refresh rotation, validate, and error paths) with a JaCoCo line-coverage gate of 85%.
