04 — Inventory Service

Distributed inventory with anti-overselling guarantees under concurrency.

Port: 8082 · Stack: Spring Boot, MySQL, Redis, Kafka

What it does

  • GET /api/inventory/{productCode} — current stock (JWT)
  • POST /api/inventory/reserve — reserve stock (JWT, idempotent)
  • POST /api/inventory/release / deduct — release or commit a reservation (JWT)
  • POST /api/inventory/demo/concurrent-reserve — load test: N concurrent reservations
  • Kafka: consumes order-created, reserves, then publishes inventory-reserved / inventory-failed

Design decisions

  • Anti-overselling under load. Reservations are protected so that 100 concurrent requests for a scarce SKU never oversell. A built-in concurrency demo endpoint proves it.
  • Idempotency. Every reservation carries a requestId; replays return the original result instead of double-reserving — essential for safe retries and at-least-once Kafka delivery.
  • Optimistic locking + Redis atomic ops for correctness without coarse-grained DB locks.
  • Event-driven. Acts as the inventory step of the order Saga (see Order).

Why it matters (skills shown)

Concurrency correctness, idempotency, optimistic locking, and bridging synchronous APIs with asynchronous Kafka workflows.
