03 — Product Service

Product catalog with a Redis caching layer. A JWT resource server (verifies tokens issued by Auth).

Port: 8081 · Stack: Spring Boot, MySQL, Redis · Security: OAuth2 Resource Server (RS256)

What it does

  • GET /api/v1/products — list active products (JWT)
  • GET /api/v1/products/hot — preloaded "hot" products (JWT)
  • GET /api/v1/products/{id} — product detail (JWT)
  • GET /api/v1/products/health — liveness (public)

Design decisions

  • Cache-aside with Redis. Reads check Redis first, fall back to MySQL, then populate the cache with a TTL. Demonstrates the most common production caching pattern.
  • Cache-stampede protection. A SETNX-based lock prevents many concurrent misses from all hammering MySQL for the same key (thundering herd).
  • TTL jitter. Randomized TTL avoids synchronized mass expiry.
  • Pure resource server. No login logic — it only validates Authorization: Bearer <jwt> using Auth's public key and a matching issuer.

Why it matters (skills shown)

Caching strategy and its failure modes (stampede, mass expiry), separation of auth concerns, and a consistent API response envelope shared across services.

Quality

Integration tests use Testcontainers (real Redis) so cache behavior is verified against an actual server, not a mock.
